1. VISIÓN GENERAL DE LA SOLUCIÓN
================================================================================

SIGETAD es un sistema de gestión de candidatos y postulaciones basado en
arquitectura orientada a servicios (SOA). La solución implementa:

- Un bus de eventos de servicio (ESB) basado en TCP (puerto 5000)
- 7 servicios independientes de negocio comunicados a través del ESB
- Gateway HTTP que actúa como cliente frontal para los servicios
- Base de datos compartida (PostgreSQL) con roles y auditoría
- Despliegue containerizado con Docker Compose
- Sistema de roles y control de acceso basado en permisos

La arquitectura desacopla los servicios permitiendo:
  * Escalabilidad independiente de cada servicio
  * Comunicación asincrónica vía bus TCP
  * Mantenibilidad modular con cada servicio en su propio dominio
  * Trazabilidad completa con sistema de historial y auditoría


2. ARQUITECTURA DEL BUS (ESB - TCP)
================================================================================

2.1 ESPECIFICACIONES TÉCNICAS
  - Protocolo: TCP Socket (NO HTTP - comunicación binaria)
  - Puerto: 5000
  - Servidor: bus/bus_server.py
  - Clientes: bus/bus_client.py
  - Librería base: bus/soa_lib.py

2.2 FORMATO DE COMUNICACIÓN
  
  Estructura de mensaje:
  ┌─────────────────────────────────────────┐
  │ [5 bytes] Longitud de payload JSON      │
  │ [5 bytes] Código del servicio (USUAR)   │
  │ [N bytes] Payload JSON                  │
  └─────────────────────────────────────────┘
  
  Ejemplo:
    Longitud: "00045"
    Servicio: "USUAR"
    Payload: {"accion": "login", "correo": "user@test.com", "password": "123"}

2.3 HANDSHAKE Y REGISTRO DE SERVICIOS

  Paso 1: Servicio se conecta al bus
  Paso 2: Envía mensaje "sinit" con su código de servicio
  Paso 3: Bus registra el servicio y habilita enrutamiento bidireccional
  
  Reconexión Automática:
    - Reintento cada 3 segundos en caso de desconexión
    - Reinicia listener del servicio
    - Recupera conexión transparentemente

2.4 CARACTERÍSTICAS DE CONFIABILIDAD

  ✓ Thread pooling para manejo de múltiples conexiones concurrentes
  ✓ Locks por servicio para garantizar thread-safety
  ✓ Respuestas estructuradas: {"ok": true/false, "error": "...", "data": {...}}
  ✓ Enrutamiento inteligente de requests/responses


3. SERVICIOS IMPLEMENTADOS
================================================================================

Se implementaron 7 servicios de dominio independientes. Cada uno tiene un
código único de 5 caracteres para identificación en el bus.

────────────────────────────────────────────────────────────────────────────

3.1 SERVICIO: USUARIOS (Código: USUAR)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Autenticación y autorización de usuarios
  • Gestión de perfiles de usuario
  • Control de intentos de login fallidos
  • Administración de roles y permisos

Modelos de datos:
  - Usuario (id_usuario, correo, contraseña, nombres, apellidos, 
             rol, estado_activo, fecha_creacion, fecha_modificacion)
  - LoginIntento (id_intento, correo, resultado, fecha_intento, 
                  intentos_fallidos_hoy)

Funcionalidades:
  ✓ Login con encriptación PBKDF2-SHA256
  ✓ Bloqueo automático después de 5 intentos fallidos
  ✓ Seguimiento de intentos de acceso fallidos
  ✓ Generación de tokens JWT-like (8 horas de TTL)
  ✓ Validación de permisos por rol

Roles implementados:
  - admin: Acceso total a todas las funcionalidades
  - analista: Acceso a búsquedas, reportes y evaluaciones
  - jefe_area: Acceso a postulaciones y vacantes del área
  - candidato: Acceso limitado a propias postulaciones

Datos de prueba (seed):
  - admin@test.com / AdminPass123
  - analista@test.com / AnalistaPass123
  - jefe@test.com / JefePass123
  - candidato@test.com / CandidatoPass123


3.2 SERVICIO: VACANTES (Código: VACAN)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Gestión del ciclo de vida de ofertas de empleo
  • Control de apertura/cierre de posiciones
  • Búsqueda y filtrado de vacantes

Modelos de datos:
  - Vacante (id_vacante, titulo, descripcion, departamento, 
             estado, fecha_creacion, creado_por_usuario, 
             fecha_modificacion, cantidad_posiciones)

Estados de vacante:
  - abierta: Disponible para postulaciones
  - cerrada: No acepta nuevas postulaciones

Funcionalidades:
  ✓ Crear nuevas vacantes
  ✓ Actualizar información de vacantes
  ✓ Cambiar estado (abrir/cerrar)
  ✓ Listar vacantes con filtros
  ✓ Búsqueda por título o descripción
  ✓ Validación de permisos (solo admin/jefe_area pueden crear)

Flujo esperado:
  estado abierta (acepta postulaciones)
    ↓
  estado cerrada (rechaza nuevas postulaciones)


3.3 SERVICIO: CANDIDATOS (Código: CANDI)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Gestión de perfiles de candidatos
  • Almacenamiento y búsqueda de información de candidatos
  • Control de archivos de candidato (CV, fotos)

Modelos de datos:
  - Candidato (id_candidato, id_usuario, profesion, experiencia, 
              telefono, ciudad, fecha_creacion, estado_disponible)
  - Carpetas de uploads: /uploads/candidatos/{id_candidato}/cv/
                        /uploads/candidatos/{id_candidato}/foto/

Funcionalidades:
  ✓ Crear perfil de candidato
  ✓ Actualizar información personal
  ✓ Búsqueda por nombre (relación Usuario.nombres)
  ✓ Búsqueda por profesión
  ✓ Gestión de disponibilidad
  ✓ Carga de CV y fotos (con validaciones)

Búsqueda:
  - Integrada con usuarios para búsquedas por nombre completo
  - Filtros por profesión y disponibilidad
  - Usado formalmente en postulaciones

Seguridad de archivos:
  - URLs firmadas con tiempo de expiración (10 minutos)
  - Validación de IP para descargas
  - Checksums SHA256 para integridad


3.4 SERVICIO: POSTULACIONES (Código: POSTU)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Control de candidaturas em vacantes
  • Gestión del flujo de selección
  • Seguimiento del estado de candidatos

Modelos de datos:
  - Postulacion (id_postulacion, id_candidato, id_vacante, 
                 estado, fecha_postulacion, notas, 
                 fecha_modificacion, id_usuario_modificacion)

Estados de postulación (flujo):
  1. postulado (estado inicial)
       ↓
  2. entrevista (seleccionado para entrevista)
       ↓
  3. evaluacion (en proceso de evaluación)
       ↓
  4. contratado (oferta aceptada)
  
  O puede transicionar a:
     rechazado (en cualquier momento)

Funcionalidades:
  ✓ Crear postulación (candidato se postula a vacante)
  ✓ Cambiar estado de postulación
  ✓ Listar postulaciones con filtros
  ✓ Búsqueda por vacante o candidato
  ✓ Una postulación por candidato-vacante (no duplicados)
  ✓ Validación de vacante abierta antes de crear postulación
  ✓ Auditoría de cambios de estado

Validaciones:
  - Vacante debe estar en estado "abierta"
  - Un candidato solo puede postularse una vez por vacante
  - Solo jefe_area o admin pueden cambiar estados
  - Transiciones de estado válidas según flujo


3.5 SERVICIO: EVALUACIONES (Código: EVALU)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Registro de evaluaciones de candidatos
  • Calificación de desempeño en entrevistas
  • Documentación de retroalimentación

Modelos de datos:
  - Evaluacion (id_evaluacion, id_postulacion, puntuacion, 
                comentarios, creado_por_usuario, fecha_creacion, 
                fecha_modificacion)

Escala de puntuación:
  - Rango: 1 a 5
  - 1: Insuficiente
  - 2: Deficiente
  - 3: Regular
  - 4: Bueno
  - 5: Excelente

Funcionalidades:
  ✓ Crear evaluación para postulación
  ✓ Una evaluación por postulación (constraint único)
  ✓ Actualizar puntuación y comentarios
  ✓ Registrar quien realizó la evaluación (usuario)
  ✓ Listar evaluaciones con filtros
  ✓ Búsqueda por postulación o candidato
  ✓ Validación de rango de puntuación (1-5)

Relaciones:
  - Cada Evaluacion está vinculada a exactly una Postulacion
  - Postulacion necesita estar en estado "evaluacion"
  - Historial registra cada creación/modificación


3.6 SERVICIO: HISTORIAL (Código: HISTO)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Auditoría completa de cambios en el sistema
  • Rastreo de quién hizo qué y cuándo
  • Mantenimiento de histórico con soft delete

Modelos de datos:
  - Historial (id_historial, tabla_afectada, id_registro, 
               tipo_cambio, cambios, usuario_id, id_postulacion, 
               fecha_cambio, is_deleted, fecha_eliminacion)

Tipos de cambio auditados:
  - CREACION: Nuevo registro creado
  - MODIFICACION: Registro existente actualizado
  - ELIMINACION: Registro eliminado (soft delete)

Información registrada:
  ✓ Tabla afectada (usuarios, candidatos, postulaciones, etc.)
  ✓ ID del registro modificado
  ✓ Tipo de cambio (creación/modificación/eliminación)
  ✓ Campo delta: antes → después
  ✓ Usuario que realizó el cambio
  ✓ Timestamp del cambio
  ✓ Postulación asociada (si aplica)

Funcionalidades:
  ✓ Registro automático de todos los cambios
  ✓ Soft delete (is_deleted, no eliminación física)
  ✓ Búsqueda por tabla, usuario o fecha
  ✓ Historial completo de postulación
  ✓ Trazabilidad de evaluaciones
  ✓ Reportes de auditoría

Migraciones:
  - 0001_initial.py: Modelo base
  - 0002_ampliar_historial.py: Campos adicionales
  - 0003_historial_postulacion_nullable.py: Relación opcional a postulación


3.7 SERVICIO: DOCUMENTOS (Código: DOCUM)
────────────────────────────────────────────────────────────────────────────

Responsabilidades:
  • Gestión de almacenamiento de archivos
  • Verificación de integridad de documentos
  • Control de acceso a descargas

Modelos de datos:
  - Documento (id_documento, nombre_original, nombre_almacenado, 
               hash_sha256, tamaño, tipo_archivo, ruta_almacenamiento, 
               id_candidato, fecha_creacion, es_privado)
  - DocumentoAuditoria (id_auditoria, id_documento, tipo_accion, 
                        id_usuario, fecha_accion, ip_remota)

Funcionalidades:
  ✓ Carga de archivos (CV, fotos, documentos)
  ✓ Cálculo de checksum SHA256 para integridad
  ✓ URLs firmadas con expiración (10 minutos)
  ✓ Validación de IP para descargas de archivos privados
  ✓ Auditoría de accesos a documentos
  ✓ Eliminación física de archivos del disco

Seguridad:
  - Archivos almacenados en /uploads/candidatos/{id}/
  - URLs firmadas previenen acceso directo
  - Validación de permisos antes de descargar
  - Cada descarga registrada en auditoría
  - TTL de 10 minutos en URLs generadas

Tipos de archivo soportados:
  - CV: .pdf, .doc, .docx
  - Fotos: .jpg, .jpeg, .png
  - Otros: .zip, .txt


4. CLIENTES IMPLEMENTADOS
================================================================================

4.1 GATEWAY HTTP - CLIENTE FRONTAL
────────────────────────────────────────────────────────────────────────────

Ubicación: backend/gateway/

Propósito:
  • Convertir peticiones HTTP en llamadas TCP al ESB
  • Ejecutar lógica de autenticación y autorización
  • Manejo centralizado de errores
  • Respuestas JSON con formato standarizado

Componentes:

  gateway/views.py
    - EndPoints HTTP que exponen la API REST
    - 20+ funciones @api_view para diferentes operaciones
    - Decorador @require_roles para control de acceso
    - Wrapper call_service() para comunicación con bus

  gateway/auth.py
    - Generación y validación de tokens
    - Encriptación de contraseñas (PBKDF2-SHA256)
    - Funciones de autenticación

  gateway/utils.py
    - Funciones utilitarias compartidas
    - Validaciones de entrada
    - Transformación de datos

  gateway/document_storage.py
    - Manejo de descargas de archivos
    - Generación de URLs firmadas
    - Validaciones de permisos

  gateway/candidate_files.py
    - Carga de archivos de candidatos
    - Validación de tipos de archivo
    - Almacenamiento en disco

4.2 PATRÓN DE LLAMADA A SERVICIOS
────────────────────────────────────────────────────────────────────────────

Estructura de respuesta HTTP:

  Success (200):
  {
    "ok": true,
    "data": {...resultado del servicio...},
    "error": null
  }

  Error (400/403/404/500):
  {
    "ok": false,
    "data": null,
    "error": "Descripción del error"
  }

Mapeo de excepciones a HTTP:
  - BusClientError → 500 Internal Server Error
  - PermissionError → 403 Forbidden
  - ValueError → 400 Bad Request
  - PreConditionFailed → 404 Not Found
  - Exception genérica → 500 Internal Server Error

Ejemplo típico de flujo:

  1. Cliente HTTP envía: POST /login
  2. Gateway valida entrada
  3. Gateway llama: call_service("USUAR", {"accion": "login", ...})
  4. Bus TCP enruta a servicio USUARIOS
  5. Servicio USUARIOS procesa y retorna resultado
  6. Gateway transforma respuesta y devuelve HTTP JSON

4.3 DECORADORES Y VALIDACIONES
────────────────────────────────────────────────────────────────────────────

@api_view(['POST', 'GET', ...])
  - Restringe métodos HTTP permitidos
  - Valida Content-Type

@require_roles(['admin', 'analista'])
  - Control de roles
  - Valida token JWT
  - Retorna 403 si permiso insuficiente

Validaciones típicas:
  - Token presente en header Authorization
  - Campos requeridos en request body
  - Tipos de dato correctos
  - Formatos válidos (email, fecha, etc.)

5.5 ORDEN DE INICIO Y DEPENDENCIAS
────────────────────────────────────────────────────────────────────────────

Secuencia de startup automática:

1. PostgreSQL inicia primero (sin dependencias)
   └─ Espera 30s para que esté listo
   
2. ESB Bus inicia (depende de DB)
   └─ Espera A que DB esté saludable
   └─ Abre puerto 5000
   
3. Django Backend inicia (depende de DB, Bus)
   └─ Ejecuta migraciones
   └─ Inicia gateway en puerto 8000
   
4. Servicios SOA inician (dependen de DB, Bus)
   └─ service_usuarios conecta como USUAR
   └─ service_vacantes conecta como VACAN
   └─ service_candidatos conecta como CANDI
   
5. Frontend inicia (depende de Backend)
   └─ Dev server en puerto 5173
   └─ Proxy a backend en 8000

Problema 1: Sincronía en un sistema supuestamente asincrónico
  - Bus está implementado en modo sincrónico (request/response)
  - No hay eventos verdaderamente asincronos
  - Acoplamiento implícito entre servicios

Problema 2: Falta de versionamiento de API
  - Sin versionamiento de contratos entre servicios
  - Cambios incompatibles rompen clientes
  - Sin negociación de versiones
  SOLUCIÓN: Agregar versionamiento en protocolo bus

Problema 3: Transacciones distribuidas complejas
  - Sin ACID entre servicios
  - Saga pattern no implementado
  - Posibles inconsistencias de datos
  SOLUCIÓN: Implementar patrón Saga o eventos compensadores

Problema 4: Seguridad en canal
  - TCP sin encriptación (TLS/SSL)
  - Sin autenticación entre servicios
  - Vulnerable a man-in-the-middle en producción
  SOLUCIÓN: Implementar mTLS entre servicios

8. PROBLEMAS ENCONTRADOS Y SOLUCIONES
================================================================================

8.1 PROBLEMA: BÚSQUEDA EN RELACIONES (DJANGO ORM)
────────────────────────────────────────────────────────────────────────────

Descripción:
  Filtros como Postulacion.objects.filter(candidato__usuario__nombre__icontains=q)
  retornaban resultados vacíos inesperadamente.

Root cause:
  - Django ORM hace JOINs implícitos en lookups de relaciones
  - Error sutil en mapeo de nombres de campos
  - Candidato tiene foreign key a Usuario (id_usuario)
  - Usuario tiene campo nombres (no name)

Solución implementada:
  Patrón de dos pasos (subquery explicit):
  
  # Antes (fallará):
  Postulacion.objects.filter(
    Q(candidato__usuario__nombres__icontains=q) | 
    Q(candidato__profesion__icontains=q)
  )
  
  # Después (funciona):
  usuarios_ids = Usuario.objects.filter(
    nombres__icontains=q
  ).values_list('id', flat=True)
  
  candidatos_ids = Candidato.objects.filter(
    Q(id_usuario__in=usuarios_ids) |
    Q(profesion__icontains=q)
  ).values_list('id', flat=True)
  
  Postulacion.objects.filter(id_candidato__in=candidatos_ids)

Documentación:
  Archivo: docs/SOLUCION_BUSQUEDA_HISTORIAL.md

Beneficio:
  - Queries más predecibles
  - Mejor optimización automática
  - Evita JOIN issues


8.2 PROBLEMA: THREADING EN BUS
────────────────────────────────────────────────────────────────────────────

Descripción:
  Condiciones de carrera al procesar múltiples conexiones simultáneamente.

Root cause:
  - Diccionario global de servicios sin sincronización
  - Múltiples threads accediendo variables compartidas

Solución:
  Implementación de locks por servicio:
  
  service_locks = defaultdict(Lock)
  
  with service_locks[service_code]:
      # Acceso exclusivo a datos del servicio

Resultado:
  - Thread safety garantizada
  - Múltiples servicios pueden operar en paralelo
  - Sin deadlocks observados


8.3 PROBLEMA: PÉRDIDA DE CONTEXTO DE USUARIO EN BUS
────────────────────────────────────────────────────────────────────────────

Descripción:
  Al procesar mensajes en bus, se perdía información del usuario

Solución:
  - Incluir id_usuario en cada mensaje del bus
  - Registrar en historial como parte del contexto
  - Auditoría completa de quién hizo qué

Implementación:
  Cada mensaje lleva:
  {
    "accion": "...",
    "usuario_id": 123,
    "timestamp": "2026-06-02T10:30:00Z",
    "ip": "192.168.1.100",
    ...
  }


8.4 PROBLEMA: INTEGRIDAD DE ARCHIVOS
────────────────────────────────────────────────────────────────────────────

Descripción:
  ¿Cómo verificar que un archivo descargado es el correcto?

Solución:
  - Cálculo de SHA256 al subir
  - Almacenamiento de hash en base de datos
  - Cliente puede revalidar al descargar
  - Checksum enviado en respuesta

Implementación:
  def calcular_checksum(ruta_archivo):
      sha256_hash = hashlib.sha256()
      with open(ruta_archivo, 'rb') as f:
          for byte_block in iter(lambda: f.read(4096), b''):
              sha256_hash.update(byte_block)
      return sha256_hash.hexdigest()


8.5 PROBLEMA: AUTORIZACIÓN GRANULAR
────────────────────────────────────────────────────────────────────────────

Descripción:
  Diferentes acciones requieren diferentes permisos

Solución:
  - Decorador @require_roles reutilizable
  - Permisos verificados antes de processing
  - Resultado: 403 si se violan permisos

Ejemplo:
  @require_roles(['admin', 'jefe_area'])
  def crear_vacante(request):
      # Solo admin y jefe_area pueden ejecutar

================================================================================

10.1 ESPECIFICACIÓN COMPLETA USUARIO A SERVICIO
────────────────────────────────────────────────────────────────────────────

FLUJO: Cliente HTTP → Gateway → Bus TCP → Servicio

Paso 1: Cliente prepara request HTTP
Paso 2: Gateway autentica (verifica token)
Paso 3: Gateway autoriza (verifica roles)
Paso 4: Gateway serializa request
Paso 5: Bus TCP enruta al servicio correcto
Paso 6: Servicio procesa y responde
Paso 7: Bus TCP retorna al gateway
Paso 8: Gateway serializa respuesta HTTP
Paso 9: Cliente recibe respuesta HTTP

10.4 EJEMPLO COMPLETO: FLUJO DE POSTULACIÓN END-TO-END
────────────────────────────────────────────────────────────────────────────

Paso 1: Candidato se autentica
  HTTP POST /login
  → Body: {"correo": "candidato@test.com", "contraseña": "..."}
  → Bus: USUAR - acción "login"
  ← Token retornado

Paso 2: Candidato ve vacantes disponibles
  HTTP GET /vacantes?estado=abierta
  Header: Authorization: Bearer <token>
  → Bus: VACAN - acción "listar"
  ← Lista de vacantes abiertas

Paso 3: Candidato crea su perfil (si no existe)
  HTTP POST /candidatos
  Header: Authorization: Bearer <token>
  → Body: {"profesion": "...", "ciudad": "..."}
  → Bus: CANDI - acción "crear"
  ← id_candidato retornado

Paso 4: Candidato sube CV
  HTTP POST /candidatos/{id}/upload_cv
  Header: Authorization: Bearer <token>
  → Body: multipart/form-data con archivo
  → Bus: DOCUM - acción "crear"
  ← URL firmada para descargar CV

Paso 5: Candidato se postula a vacante
  HTTP POST /postulaciones
  Header: Authorization: Bearer <token>
  → Body: {"id_candidato": 10, "id_vacante": 42}
  → Bus: POSTU - acción "crear"
  ← id_postulacion: 100, estado: "postulado"
  → Bus: HISTO - registra CREACION
  
Paso 6: Jefe de área ve postulaciones
  HTTP GET /postulaciones?vacante=42
  Header: Authorization: Bearer <token_jefe>
  → Bus: POSTU - acción "listar"
  ← Lista de postulaciones para vacante
  
Paso 7: Jefe cambia estado a "entrevista"
  HTTP PUT /postulaciones/100
  Header: Authorization: Bearer <token_jefe>
  → Body: {"nuevo_estado": "entrevista", "notas": "..."}
  → Bus: POSTU - acción "cambiar_estado"
  ← Nuevo estado confirmado
  → Bus: HISTO - registra MODIFICACION con delta
  
Paso 8: Jefe cambia estado a "evaluacion"
  HTTP PUT /postulaciones/100
  → Body: {"nuevo_estado": "evaluacion"}
  → Bus: POSTU - acción "cambiar_estado"
  ← Estado actualizado
  → Bus: HISTO - registra cambio
  
Paso 9: Evaluador crea evaluación
  HTTP POST /evaluaciones
  Header: Authorization: Bearer <token_evaluator>
  → Body: {"id_postulacion": 100, "puntuacion": 4, "comentarios": "..."}
  → Bus: EVALU - acción "crear"
  ← id_evaluacion: 50
  → Bus: HISTO - registra CREACION
  
Paso 10: Jefe cambia estado a "contratado"
  HTTP PUT /postulaciones/100
  → Body: {"nuevo_estado": "contratado"}
  → Bus: POSTU - acción "cambiar_estado"
  ← Candidato ha sido contratado
  → Bus: HISTO - registra cambio
  
Paso 11: Admin consulta auditoria
  HTTP GET /historial/postulacion/100
  Header: Authorization: Bearer <token_admin>
  ← Historial completo de la postulación con:
    - Creación por candidato
    - 3 cambios de estado por jefe
    - Evaluación agregada
    - Timestamps y usuarios

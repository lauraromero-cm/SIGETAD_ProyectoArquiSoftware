================================================================================
OPERACIONES DE AUDITORÍA Y HISTORIAL MEJORADAS - SIGETAD
================================================================================

Documento que especifica las nuevas operaciones de auditoría implementadas en 
el Servicio de Historial (HISTO) para garantizar inmutabilidad, trazabilidad 
completa y capacidad de reportes.

================================================================================
1. CAMBIOS IMPLEMENTADOS AL MODELO HISTORIAL
================================================================================

NUEVOS CAMPOS EN TABLA 'historial':

cambios_detalles (JSON)
───────────────────────
- Tipo: JSONField
- Almacena cambios estructurados: {campo, valor_anterior, valor_nuevo}
- Ejemplo:
  {
    "campo": "estado",
    "valor_anterior": "postulado",
    "valor_nuevo": "en_revision"
  }

is_deleted (Boolean)
────────────────────
- Tipo: BooleanField
- Default: False
- Propósito: Soft delete (marcar como eliminado sin borrar físicamente)
- Garantiza inmutabilidad del historial

fecha_eliminacion (DateTime)
────────────────────────────
- Tipo: DateTimeField (nullable)
- Se completa cuando un evento se marca como eliminado
- Auditoría de eliminaciones

id_entidad_tipo (String)
────────────────────────
- Tipo: CharField (choices)
- Opciones: 'postulacion', 'vacante', 'candidato', 'usuario', 'evaluacion'
- Permite auditar no solo postulaciones sino cualquier entidad

id_entidad_referencia (BigInteger)
──────────────────────────────────
- Tipo: BigIntegerField (nullable)
- ID de la entidad siendo auditada
- Ejemplo: si tipo='vacante', referencia=5 → audita vacante con id_vacante=5

NUEVOS ÍNDICES PARA OPTIMIZACIÓN:

- idx_hist_usuario_fecha: (id_usuario, fecha DESC)
  → Auditar acción de usuario X es O(log n)

- idx_hist_entidad_fecha: (id_entidad_tipo, id_entidad_referencia, fecha DESC)
  → Timeline de cambios a una entidad es O(log n)

- idx_hist_tipo_fecha: (tipo, fecha DESC)
  → Filtrar por tipo de evento es O(log n)

CONSTRAINT DE INTEGRIDAD:

CHECK historial_immutable_check:
  (is_deleted = false OR fecha_eliminacion IS NOT NULL)
  
  Garantiza:
  - Si is_deleted = true, DEBE tener fecha_eliminacion
  - Si is_deleted = false, fecha_eliminacion DEBE ser NULL
  - Evita inconsistencias

OPERACIÓN 5: soft_delete_evento
════════════════════════════════

Propósito: Marcar un evento como eliminado SIN BORRAR FÍSICAMENTE (inmutabilidad)

Contrato:
─────────
{
  "action": "soft_delete_evento",
  "data": {
    "id_historial": 125  // REQUERIDO: ID del evento a marcar como eliminado
  },
  "user": {...}
}

Restricción: Solo admin

Respuesta:
──────────
{
  "ok": true,
  "data": {
    "mensaje": "Evento marcado como eliminado",
    "id_historial": 125
  }
}

Efecto:
- is_deleted = true
- fecha_eliminacion = ahora
- Evento NO aparece en listar_historial (filtro is_deleted=False)
- Evento SIGUE EN BD para auditoría forense

¿Cuándo usar?
- Error administrativo: "Registramos mal este evento, marcarlo como eliminado"
- Mandato legal: Necesitamos que algo desaparezca pero dejar rastro

3. PROTECCIÓN CONTRA ELIMINACIÓN (INMUTABILIDAD)
================================================================================

ANTES (INSEGURO):
────────────────
DELETE FROM historial WHERE id_historial = 125;
→ ¿Quién lo eliminó? ¿Cuándo? ¿Por qué? NO HAY RASTRO.

DESPUÉS (SEGURO - SOFT DELETE):
───────────────────────────────
POST /api/historial {
  "action": "soft_delete_evento",
  "data": {"id_historial": 125}
}

Resultado:
- UPDATE historial
  SET is_deleted = true, 
      fecha_eliminacion = NOW()
  WHERE id_historial = 125;

- El evento SIGUE EN LA BD (¿quién lo eliminó?, marca de tiempo)
- Query de auditoría sigue viendo: "Fue eliminado el 28/05 a las 16:00"
- No aparece en reportes normales (is_deleted=false)
- Pero está para auditoría forense si necesitan investigar


CONSTRAINT DE INTEGRIDAD EN BD:
───────────────────────────────
CHECK (is_deleted = false OR fecha_eliminacion IS NOT NULL)

Garantiza:
✅ Si alguien intenta UPDATE es_deleted=true sin fecha → ERROR
✅ Si alguien intenta UPDATE es_deleted=false CON fecha → ERROR
✅ Integridad referencial garantizada a nivel BD

5. TABLA COMPARATIVA: ANTES vs. DESPUÉS
================================================================================

ASPECTO                    │ ANTES          │ DESPUÉS
───────────────────────────┼────────────────┼─────────────────────────────
Auditoría por usuario      │ ❌ No          │ ✅ SI - operación auditar_usuario
Timeline de entidad        │ ❌ Manual      │ ✅ SQL - operación auditar_entidad
Cambios detalledosistema           │ ❌ Solo texto  │ ✅ JSON - {campo, anterior, nuevo}
Eliminación de eventos     │ ❌ DELETE      │ ✅ Soft delete - is_deleted=true
Trazabilidad de eliminación│ ❌ No          │ ✅ SI - fecha_eliminacion
Exportación a CSV          │ ❌ No          │ ✅ SI - exportar_historial_csv
Inmutabilidad              │ ❌ No          │ ✅ CHECK constraint en BD
Reportes de cambios        │ ❌ No          │ ✅ SI - reporte_cambios_entidad
Protección del historial   │ ⚠️  ORM level  │ ✅ BD level + ORM level
